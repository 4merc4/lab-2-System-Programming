# Лабораторна 2. Вимірювання та аналіз продуктивності

Досліджувана програма: множення матриць N×N (double), N = 1024, файл `matmul.c`.
- `naive`: цикл i-j-k, зібрана з `-O0` (стан «до»).
- `keys_only`: той самий код `naive`, зібраний з `-O3 -march=native` (вплив лише ключів).
- `opt`: цикл i-k-j, зібрана з `-O3 -march=native` (стан «після»).

Середовище: Windows + WSL2 (Ubuntu), AMD Ryzen 5 5600 (Zen 3, AVX2/FMA, без AVX-512), gcc 15.2, perf 7.0.14.
Відтворення: `./run_all.sh` (збірка, FlameGraph, `time -v`, `perf stat/record/report`).

## 1. FlameGraph
Файли: `flame_before.svg`, `flame_keys_only.svg`, `flame_after.svg` (побудовані через `perf record -g` + FlameGraph Брендана Грегга).
- До: майже вся ширина (~99.5%) належить `matmul_naive`; `main` і виклики libc лише формують основу стеку.
- Після: `matmul_opt` займає ~82%; стали помітні `rand` (~3.6%) та ядерні виклики (обробка page faults при ініціалізації) — програма стала настільки швидкою, що її «обв'язка» видна на графіку.

## 3. Енерговитрати
Метод: HWiNFO (Sensors-only), датчик CPU Package Power, середнє значення (Average) після скидання лічильників. RAPL у WSL недоступний.
Спокій виміряно 39 с без навантаження: P_idle = 28.894 Вт. Навантаження — цикл запусків: `naive` 12 разів (52.761 с), `opt` 450 разів (56.888 с).
- 3.1 Система (CPU Package Power): E = P_load × t.
- 3.2 Лише програма: E = (P_load − P_idle) × t.

## 4. Порівняння до та після оптимізації

### 4.1 Асемблер (godbolt, gcc 16.2, `-O0` проти `-O3 -march=znver3`)
- `-O0`: всі змінні читаються й пишуться через стек (`[rbp-…]`), індекси перераховуються (`movsxd`, `cdqe`, `imul`, `lea`) на кожній ітерації; ~39 інструкцій на одне число, скалярні `movsd`, `mulsd`, `addsd`.
- `-O3`: змінні в регістрах, цикл розгорнуто й векторизовано.
- `matmul_naive` з `-O3`: векторизація лише часткова (`vmovsd` + `vmovhpd` збирають стрибкові елементи `B`, `vmulpd xmm`, `vaddsd`), порядок додавання збережено; вузьке місце — доступ до пам'яті, тому `-O3` без зміни алгоритму не прискорив програму.

### 4.1.1 AVX-інструкції (`matmul_opt`, цикл `.L34`)
- `vbroadcastsd ymm1, xmm2` — розмножує `a` на 4 double.
- `vmovupd ymm0, [..]` — читання 4 double з `B`.
- `vfmadd213pd ymm0, ymm1, [..]` — `C += a·B` для 4 double однією інструкцією (FMA).
- `vmovupd [..], ymm0` — запис 4 double в `C`.
- `add r8, 32` — крок 4 double. Залишок обробляється `vfmadd132pd xmm` (2 числа) і `vfmadd132sd` (1 число).

ymm = 256 біт = 4 double (AVX2).

### 4.2 Час та інші показники
Таблиця з пункту 2: wall time 4.39 с → 0.12 с (~36×), інструкцій 34.6 → 1.15 млрд (~30× менше), циклів 19.9 → 0.55 млрд, IPC 1.7 → 2.1, абсолютна кількість L1-промахів 1.25 → 0.15 млрд. `-O3` без зміни порядку циклів час не покращив (4.39 → 4.82 с, IPC 0.3).

### 4.3 FlameGraph після оптимізації
`flame_after.svg`: `matmul_opt` ~82% замість ~99.5%; з'явилась помітна частка ініціалізації (`rand`) та ядерних викликів.

### 4.4 Енерговитрати
Потужність під навантаженням зросла (37.79 → 42.72 Вт, +13%): щільніша робота ядра (IPC 2.1 проти 1.7) і 256-бітні векторні інструкції. Але час одного запуску зменшився у ~35 разів, тому енергія на один запуск впала: система 166.2 → 5.40 Дж (~31×), лише програма 39.1 → 1.75 Дж (~22×). Енергія = потужність × час: виграш у часі значно перевищує зростання потужності.
